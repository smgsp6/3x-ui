## 正式发行前不得忽略的风险

1. **上游镜像基座为可变标签。** `Dockerfile` 使用 `node:26-alpine`、`golang:1.27-alpine` 和 `alpine`。正式镜像必须在审核多架构支持后固定各基座镜像 digest；预览版不直接覆盖上游 Dockerfile。
2. **构建时动态下载二进制与规则。** `DockerInit.sh` 使用 Xray 的版本标签、mtg-multi 的 latest API 及多个 geodata latest 下载来源，缺少统一的下载文件摘要验证。正式 Vela 构建需要有固定版本/哈希、故障中止、供应链审查和可复现的发布清单，而非未审查的自动 latest。
3. **容器权限与网络隔离。** 原版 `docker-compose.yml` 带 `NET_ADMIN`、`NET_RAW`，默认只映射管理端口；Vela 独立 Host Network 模板保留 Xray 动态 TCP/UDP 需求，但具有更大宿主机网络影响面。正式部署必须完成管理入口仅本机绑定、可信 HTTPS 反向代理、最小能力测试与入站实际联调，不要通过删减原版功能草率解决。
4. **运行期私人文件必须留在服务器本地。** Bot Token、管理员 ID、数据库、客户信息、节点资料、证书私钥、备份不能出现在 Docker build context、镜像历史层、Git 历史或 GitHub Actions 日志。现有开发 CI 只与固定上游基线做隐私差异审查；上游历史里已有 24 个 PEM 格式告警，需要在生产发布前分别核对，不可称全历史零告警。
5. **构建通过不是启动验收。** 仍须在独立测试环境验证完整容器启动、持久化数据卷、HTTPS/Telegram Mini App、会话权限、Xray 协议与多节点、实际备份恢复、签名升级和中断回滚。生产发布签名公钥/私钥、签名清单和发行镜像尚未配置。
