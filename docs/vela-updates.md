# Vela 安全更新说明（开发预览）

**当前没有正式 Vela 镜像，也没有发布 `stable.json`。**
本阶段的 CLI 是供审查和模拟环境测试的实现，不应复制到实际生产服务器。

## 稳定更新链路

1. 从 `MHSanaei/3x-ui` 同步源码到本仓库 `smgsp6/3x-ui` 的独立 PR，先审核安全和兼容性。
2. CI 进行 Go 单元测试、前端构建、静态扫描、依赖扫描、Docker 构建、Mini App 及 Xray 回归测试。
3. 维护者审核通过后，正式发布镜像到 `ghcr.io/smgsp6/3x-ui`，记录**不可变 SHA256 Digest**；不直接运行上游 `update.sh`。
4. 在本仓库 `main` 发布安全审查过的 `deploy/vela/stable.json` 和独立 Ed25519 签名 `stable.json.sig`，包含 `repository`、`channel`、单调递增正整数 `releaseSequence` 和不可变 `image` 摘要。**清单、签名和正式公钥尚未创建**。
5. 安装后的 `vela update` 只从本 Fork 拉取发布清单，拒绝不是该镜像仓库的地址、浮动标签和非法摘要。
6. 下载镜像成功后，停止旧服务，对 SQLite 数据库、证书与 ACME 状态做一致性备份并校验归档。**旧服务保持停止直到候选镜像启动**，消除备份后写入丢失窗口；健康检查失败恢复旧镜像与旧数据。
7. 逐台更新服务器，先验证金丝雀节点；对数据库向前迁移，应额外执行可恢复性测试。

## 部署网络和权限注意事项

原版 `docker-compose.yml` 中 `2053:2053` 仅公开管理端口，不能覆盖任意新建的 TCP/UDP 入站端口。Vela 的候选方案采用 `network_mode: host` 来保持完整 Xray 监听能力；在 Vela 模式中 Go Web 管理监听地址强制为 `127.0.0.1`，必须搭配**独立 HTTPS 反向代理**才能供 Telegram Mini App 使用。远程节点 API 需通过受保护的反向代理、mTLS 或可信内网访问。

原版 Fail2ban/IP 限制能力使用容器 `NET_ADMIN` 和 `NET_RAW`，在 Host Network 下影响宿主机防火墙，**这是明确的高权限风险**，不是安全沙箱。仍需评估更小权限的替代架构并做实机测试，不能简单宣布容器隔离安全。

## 当前 CLI 的约束

`deploy/vela/vela` 仅包含（均未获得生产部署许可）：

- `vela status`：只读检查当前镜像、容器状态和 Vela 专属健康接口；`vela logs`：本地查看最近的容器日志，请勿公开。
- `vela doctor`：检查本机 Docker Compose 配置及镜像 Digest。
- `vela backup`：停止面板进程后制作 `db`、`cert`、`acme` 的本地归档，并重新启动。
- `vela update`：获取本仓库的 stable 清单、拉取 Digest 镜像、备份、更新、健康检查、失败恢复。

正式 CLI 安装器和发布管线还没有接入，不能声称一键安装已可用。所有私密数据（Bot Token、SQLite、证书、ACME 账户）留在服务器本地；备份包含证书和账户资料，因此应确保目录权限严格，异地备份需另外加密。

## 第五阶段增加的防误判与隐私保护

- 只有 Vela 新增的 `/tg-miniapp/health` 返回 HTTP `204` 才通过本地健康检查；接口内部检查 Mini App 模式、Bot Token 可读和管理员数据库可访问。**它仍然只是基础存活检测**，不验证客户端协议实际可用。
- 构建 Docker 镜像时，`.dockerignore` 过滤私密运行文件，避免 `Dockerfile` 中的 `COPY . .` 将数据复制到中间层或远端构建缓存。
- 安装目录不得允许其他用户写入，脚本拒绝利用符号链接替换锁文件和备份目录。
- 当前稳定发布清单仍缺签名与外部信任锚；固定 Digest 防止意外使用浮动标签，**不能单独证明镜像来源可靠**。不能用于生产自动更新。

## 第六阶段补充：异常中断恢复

更新器先写入本地 `.pending-update`，再执行暂停与一致性备份；成功通过 Vela 专属健康检查后，才写入新镜像摘要并清理记录。检测到未完成的升级时禁止继续更新，避免覆盖原有恢复点。

`vela recover` 会核对记录中的原镜像摘要和本地归档路径，检查备份成员是否安全，然后恢复原镜像及原始数据；异常候选版本的数据留在本地 `failed-updates/`。这些目录包含敏感数据库和证书，严禁提交到 GitHub 或公开上传。恢复命令仍需在真实 Docker 环境中验证后才可作为正式维护功能使用。

## 第七阶段：签名清单与端口兼容

`vela update` 在下载镜像前必须验证来自维护者离线 Ed25519 密钥的清单签名，且校验本地公钥文件的固定 SHA256 指纹。**本预览版故意没有真实的固定公钥指纹**，因此更新命令拒绝执行，防止误将未审核的远程 JSON 当成生产版本。详见 [发行签名方案](RELEASE-SIGNING.md)。

部署模板显式配置 `XUI_PORT`（默认 2053），健康检查读取同一端口而不执行 `.env` 中的任何 Shell 内容。`vela recover` 在有待恢复记录时允许中断造成的部分数据目录缺失，并重新恢复归档；这仍需要在真实 VPS 上演练。

## 第八阶段：签名版本序号防重放

- 下载清单并验证 Ed25519 签名后，才读取 `releaseSequence`。它必须是 JSON 整数（不是字符串或布尔值），范围 1…9007199254740991。
- 每台服务器的 `<VELA_HOME>/release.sequence` 必须由**经过审核的安装器**初始化为可信基准（新部署可为 0）。文件缺失时更新器会拒绝操作，防止因丢失本地状态而接受旧签名清单。
- 发行序号小于本地记录的版本时拒绝更新；序号相同但镜像 Digest 不同也拒绝。完整镜像标识仍须匹配唯一 Fork 的 GHCR 地址。
- 成功更新后以安全文件替换记录新序号；升级失败或意外中断恢复旧镜像时，同时恢复相应序号。保护并不是外部审计、公钥撤销或真实 Docker 演练的替代。
- **本版本仍未发布正式签名密钥、镜像或自动安装器，不能在生产机运行。**
